# 调优方法论与一个可复用的 Skill 设计

把调优过程提炼成一个 Skill：让任何 Agent 在任意符合 Strata 要求的机器上，
都能把配置调到接近最优。

本文按「搜索顺序 + 量化判据」组织：为什么做成 Skill、适用范围、设计原则、
完整流程、不要做的清单、测量纪律，最后是本机最终配置。

---

# Skill 设计

## 为什么要做成 Skill

调优的难点通常不是「知识不足」，而是**搜索顺序**：容易在显存、内存、PCIe
这些「引擎内部」上花大量时间，而真正的瓶颈往往在 CPU 调度、请求参数、
上下文长度这些「引擎外部」。

所以 Skill 的价值不在提供答案，而在**提供一个不会漏掉整类可能性的搜索顺序**，
并且每一步都有**量化的判据**，而不是靠「感觉快了」。

## Skill 的适用范围

**前提条件**（任一不满足则本 Skill 不适用）：

| 项 | 要求 |
| --- | --- |
| 推理框架 | Strata（Terminal 或源码安装均可） |
| GPU | NVIDIA，≥ 12 GB 显存 |
| 平台 | Windows 或 Linux |
| 模型 | Strata 支持的 MoE 模型（Qwen3.8-Flash-Next 全家 / DeepSeek-V4.1） |

**不适用**：AMD 卡、≤ 8 GB 显存、llama.cpp/Ollama 等其它框架。

## 设计原则

一个「自动调优」的 Skill 最容易犯的错是变成一个参数清单。所以定了三条：

### 原则 1：先测基线，再动任何参数

没有基线就无法判断收益真假。小样本很容易把噪声当成收益：
+7.5% 的 ATTN_DAILY、+20% 的 pcie-frac、单次样本的「关思考代码更多」，事后看都在噪声里。

**强制要求**：每个改动必须和同一时刻的基线对比，至少 3 轮，看区间是否重叠。

### 原则 2：按「收益/成本」排序，而不是按熟悉度

正确的顺序应该是：

```
1. 请求参数（/effort）        —— 5.4 倍，零成本，不用改任何配置
2. 系统调度（pool-workers）    —— 可用性问题，1 分钟
3. 缓存策略（conversation）    —— 1.5 倍，一个参数
4. 引擎参数（prefill 等）      —— 2 倍，一个参数
5. 内核开关（MMQ_DIRECT 等）   —— 通常 <5%，且多半不生效
6. 显存/内存调优              —— 只在上述都做完后才考虑
```

**常见的错误顺序正相反**：从显存开始，一路往下。

### 原则 3：区分「三个不同的速度指标」

混用会导致所有结论失真：

| 指标 | 含义 | 典型值（本机 RTX 4080） |
| --- | --- | ---: |
| **decode 速度** | 每 token 生成速度 | 60–95 tok/s |
| **prefill 速度** | 读提示词速度 | 2000 tok/s（auto）/ 1000（2048） |
| **端到端速度** | 输出 token / 墙钟时间 | 4–50 tok/s（差异巨大） |

用户的体感对应的是**端到端**。而调优通常优化的是前两个。
**Skill 必须在最后用端到端速度做验收。**

## Skill 的完整流程

### 阶段 0：采集基线（必须，约 5 分钟）

不采集基线就往下走，后面所有数字都无法判断真假。

```
0.1  硬件与版本
     nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv
     strata --version

0.2  服务能起
     strata launch --preset <任意档位>
     curl http://127.0.0.1:8080/health
     记录：max_context / loaded

0.3  三个速度指标（各 3 轮，取中位）
     - prefill：发一个 8K 提示词，读 timings.prompt_per_second
     - decode：发一个 300 token 请求，读 timings.predicted_per_second
     - 端到端：同一个请求的 output_tokens / 墙钟秒数

0.4  系统健康
     (Get-Counter '\System\Processor Queue Length')  ← Windows
     cat /proc/loadavg                                ← Linux
     记录空闲内存、显存余量
```

**基线表**（填完才继续）：

| 指标 | 基线值 | 备注 |
| --- | ---: | --- |
| prefill tok/s | | |
| decode tok/s | | |
| 端到端 tok/s | | |
| CPU 队列 | | |
| 空闲内存 | | |
| 显存余量 | | |

### 阶段 1：请求参数（最高优先级，零成本）

**这一步不需要改任何配置，只改请求。**

#### 1.1 思考预算

先测量思考占比：

```
发一个生成类任务（比如「写一个单文件 HTML 画 XX」），max_tokens 给大
读 usage.completion_tokens 和 message.reasoning_content 的长度
```

判据：

| 思考字符 / 总输出 | 诊断 |
| --- | --- |
| > 70% | **思考过重，这是最大的优化点** |
| 30–70% | 有优化空间 |
| < 30% | 跳过这一步 |

如果思考过重，按顺序试：

| 档位 | 适用于 | 本机实测（鹈鹕测试） |
| --- | --- | ---: |
| `medium` | 生成类任务，保留规划能力 | **57.4 s，结构最好** |
| `none` | 一次性原型 | 37.4 s |
| `low` | — | 未测 |
| `high`（默认） | 调试、分析、数学 | 311.7 s |

**怎么传**（按框架分）：

| 场景 | 做法 |
| --- | --- |
| Claude Code | 用户手动 `/effort medium`（写配置无效，见下） |
| 直接调 API | 请求体加 `"reasoning_effort": "medium"` |
| Anthropic 协议 | `"output_config": {"effort": "medium"}` |

**为什么不能写进服务端配置**：

```python
# serve/server.py
elif not req.get("thinking") and not req.get("output_config"):
    req["output_config"] = {"effort": effort}
```

客户端只要带了 `output_config`（Claude Code 100% 都带），配置就被覆盖。
**Skill 必须提醒 Agent：不要在这上面浪费时间。**

#### 1.2 请求形状（影响缓存复用，容易被忽略）

**判据**：读引擎日志的复用率。

```
grep "prompt .* tokens = .* reused" <engine.log>
```

| 复用率 | 诊断 | 处理 |
| --- | --- | --- |
| > 95% | 正常 | — |
| 50–95% | 部分失效 | 查是否多会话交替（阶段 3） |
| **< 50% 且成串出现** | **请求形状有问题** | 见下 |

**关键规则**：`user` / `assistant` 交替的 messages 能复用 99.9%；
单条不断增长的 `user` 消息只能复用 87.8%（受 checkpoint 间隔限制）。

**差异是 8.7 倍**（每轮 0.3 秒 vs 2.6 秒）。

---

### 阶段 2：系统调度（可用性问题，1 分钟）

**这一步解决的不是速度，是「机器还能不能正常用」。**

#### 判据

在一台正在跑推理的机器上试打字。如果卡：

```
Windows: (Get-Counter '\System\Processor Queue Length').CounterSamples.CookedValue
Linux:   cat /proc/loadavg 的第四段（running/total）
```

| CPU 队列 | 诊断 |
| ---: | --- |
| < 5 | 正常 |
| 5–20 | 开始有感觉 |
| **> 50** | **界面会卡死** |

本机实测：默认配置下队列 **131.7**，一个普通线程要等 **186.9 ms**。

#### 处理

```
--pool-workers <N>
```

**扫描方法**：从物理核数的一半开始，每次加 2，测：

1. decode 速度（应该基本不变）
2. CPU 队列（应该 < 5）

本机结果：

| workers | 队列 | decode |
| ---: | ---: | ---: |
| 4 | 0.3 | 82.8 |
| 6 | 1.3 | 88.9 |
| **10** | **2.7** | **90.0** |
| 12 | 3.3 | 91.8 |
| **15（默认）** | **46.7** | 91.1 |

**关键观察：decode 几乎不变，唯一断崖是队列。**
所以选 worker 数的唯一判据是「队列 < 5 且 decode 不掉」。

**反直觉**：减少 worker 有时让 decode **更快**（本机 +6%）——
线程争抢和内存带宽竞争本身就是开销。

---

### 阶段 3：缓存策略（多会话场景，1 个参数）

#### 判据

看引擎日志里有多少请求是零复用：

```
grep "prompt .* tokens = 0 reused" <engine.log> | wc -l
```

如果**成串出现且长度在两个值之间反复跳变**（例如 `178780` ↔ `54333`），
说明是**多个会话交替**，checkpoint 互相挤掉。

本机实测：244 个请求里 102 个（42%）零复用，累计重读 **138.6 分钟**。

#### 处理

```
--conversation-cache-mib <N>
```

**N 怎么定**：按会话快照大小算，实测约 **23–32 KiB/token**。

| 最大会话 | 需要 |
| ---: | ---: |
| 50K | 约 1.2 GiB |
| 120K | 约 2.8 GiB |
| 200K | 约 4.7 GiB |

**同时有 2 个大会话**就把两者相加。本机用了 8192 MiB（覆盖 180K + 54K）。

**注意**：默认是**自动计算**的，但通常算出来是 0（关闭）——
因为模型加载后引擎看到的空闲内存已经很少了。**必须显式指定。**

**不要加** `--conversation-cache-min-tokens`：实测会让短会话完全失去缓存，
反而更慢。

---

### 阶段 4：引擎参数（在以上都做完之后）

#### 4.1 prefill 分块

```
--prefill auto
```

**判据**：测 8K 提示词的读取速度。

| 值 | 本机实测 |
| --- | ---: |
| `2048` | 998.8 tok/s |
| `4096` | 1,682.7 |
| **`auto`** | **2,219.4** |
| `16384` | 2,094.9 |

**用 `auto` 而不是写死值**：引擎会按当时的显存余量选最大可行分块，
换档位时自动适配。

#### 4.2 专家缓存

```
--expert-cache 4096
```

这是**下限，不是实际值**。引擎会按可用显存自动扩（本机扩到 4292 或 6295 槽）。
**手动往上调没有意义**，实测二次确认过。

---

### 阶段 5：内核开关（通常无功而返）

**先检查能不能用**：

```
STRATA_MMQ_DIRECT=1 <启动>
```

如果日志出现：

```
STRATA_MMQ_DIRECT=1 is ignored: this build has no pointer-table MMQ
```

说明预编译版没开 `-DSTRATA_MMQ_TAB`，**直接放弃这一档**。

**其它内核开关**（`STRATA_ATTN_DAILY` 等）：
先查引擎文档的架构支持表。如果目标卡的 compute capability 不在表内
（例如 sm_89/RTX 40 就不在任何表里），**这些开关大概率无效**。

本机实测：`STRATA_ATTN_DAILY=1` 6 轮后 +1.0%，在噪声内。

---

### 阶段 6：验收

**速度和质量必须一起验。只测速度，会调出"很快但答错"的配置。**

这是本文最该强调的一点：只用「结构分」（函数数、动画相位、近/远端建模）
当代理指标是**不够的**——它只在一个任务上测过，权重是人为定的，
且**无法判断「有没有变差」**。
而调优的核心风险恰恰是：为了快，把效果调坏了。

#### 6.1 数量验证：用内置基准

Strata 自带 `strata bench`，`standard-v1` 套件设计上就是干这个的：

```bash
strata bench run --profile "<档位>" --track default --track-notes "before"
# 改配置
strata bench run --profile "<档位>" --track default --track-notes "after"
strata bench compare <run1目录> <run2目录>
```

| 阶段 | 内容 | 请求数 |
| --- | --- | ---: |
| Warm-up | 短提示词 | 1（不计分） |
| Performance | short / prompt-4k / prompt-16k × 3 轮 | 9 |
| **Sanity** | **I1–I4 / R1–R4 / T1–T4** | **12** |

**Sanity 的 12 项带冻结的期望答案**，是"效果有没有坏"的硬判据：

| 类别 | 测什么 | 例子 |
| --- | --- | --- |
| I（指令遵循） | 严格输出格式 | `I1`: 只返回 `{"ok":true,"count":3}` |
| R（长上下文检索） | 4K–16K 里找指定信息 | `R1`: 问 `access_code`，期望 `ORBIT-731` |
| T（工具调用） | 正确发起调用 | — |

**判据：性能提升，且 12 项 sanity 全过。**

`compare` 会做 workload 校验——工作量不一致就拒绝比较。

**局限**：`--profile` 走服务端配置，只能验证引擎参数。
请求级改动（`reasoning_effort`）覆盖不到，需要 6.2。

#### 6.2 请求级改动要盲评

`/effort` 这类只能人工评，但**必须盲评**。

知道某份产物是哪个档位生成的，再说它「结构最好」，就无法排除这层偏向。

做法：同一提示词每个配置生成 3 次（不同 seed）→ 打乱重命名成 `A1..F6`
→ 只看文件名打分 → 最后揭示。

#### 6.3 稳定性：同配置跑 3 次

**单次结果不能比较。** 本机实测同一配置两次差 **24%**（11,239 vs 9,048 字符）。
两个配置的区间**不重叠**才算有差异。

#### 6.4 端到端速度

本机的验收结果：

| 项 | 改造前 | 改造后 | 倍数 |
| --- | ---: | ---: | ---: |
| 画图任务端到端 | 311.7 s | **57.4 s** | **5.4x** |
| 读 8K 提示词 | 998.8 tok/s | 2219.4 | 2.2x |
| 两会话交替复用 | 0/8 | 8/8 | — |
| CPU 队列 | 131.7 | 2.0 | — |

#### 6.5 报告必须说清三种边界

| 边界 | 说明 |
| --- | --- |
| 硬件上限 | 显存带宽、模型装不下——软件改不动 |
| 未验证项 | 哪些没盲评、哪些只测了一次 |
| 失效条件 | 如 `/effort medium` 只在生成类任务成立，调试要调回去 |

## Skill 必须附带的「不要做」清单

这些是在本机花了时间才排除的，写进 Skill 可以省掉后来者：

| 不要 | 原因 |
| --- | --- |
| 装 CUDA Toolkit | 预编译引擎自带运行时 |
| 开 `STRATA_MMQ_DIRECT` | 预编译版不支持，引擎会明确拒绝 |
| 手动开架构内核开关（sm_89 等） | 不在支持表内，实测 +1% 在噪声内 |
| 加 `--conversation-cache-min-tokens` | 短会话失去缓存，更慢 |
| 加 `--max-queue 0` | 引擎本来只跑一个请求，限制只让后来的早点失败 |
| 用 session files 存盘恢复 | 启动器重写 run config，字段被抹掉 |
| 靠改 GPU 功耗解决 USB 掉电 | 13 次实测无效 |
| 为省显存把 `--prefill` 压到 2048 | 省下的显存不紧张，代价是慢一倍 |
| 把服务端 `reasoning_effort` 当作生效 | 被请求的 `output_config` 覆盖 |

## 测量纪律（这部分比参数更重要）

小样本太容易把噪声当收益，所以必须写成硬规则：

### 规则 1：小样本的正面结果先当噪声

| 案例 | 3 轮结果 | 6 轮结果 |
| --- | ---: | ---: |
| `STRATA_ATTN_DAILY` | +7.5% | **+1.0%（噪声）** |
| 单次样本「关思考代码更多」 | 代码 +44% | **重复测差 24%，是噪声** |

**至少 3 轮；结论要建立在区间不重叠上。**

### 规则 2：交错测，不要成块测

```
成块：A A A B B B     ← 机器状态漂移会全部算到 B 头上
交错：A B A B A B     ← 漂移被两边平摊
```

本机基线在半小时内从 76.8 漂到 58.9（30%），**比任何待测差异都大**。

### 规则 3：区分冷启动和稳态

第一条请求总是慢（专家缓存还没学到路由）。
**第一轮永远作为预热丢弃。**

### 规则 4：换指标之前先怀疑指标本身

反例：用「Python 线程调度延迟」当界面卡顿的代理指标，
第一次测出 186.9 ms，重测只有 0.2 ms——**这个指标不可靠**。
而 CPU 队列在两次测量里都是可靠的（131.7 / 46.7）。

**当一个指标的结果和体感矛盾时，先怀疑指标，别急着改参数。**
